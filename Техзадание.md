Техническое задание: LLM Test Bench
Приложение для Windows для автоматизированного тестирования локальных языковых моделей (GGUF) в режимах чата и агента, с сохранением результатов, историей и сравнением прогонов.

1. Общие сведения
Назначение: тестирование локальных LLM (llama.cpp / GGUF) через llama-server (HTTP API).

Режим работы: серверный. Прямой запуск через llama-cpp-python (п. 3.3) отложен до появления сборок под GPU sm_120 / CUDA 13.x — готовых колёс нет, сборка из исходников на целевой машине не поднималась.

Приложение не запускает свой сервер по умолчанию: модель грузит лаунчер, приложение тестирует то, что уже слушает на host:port. Поэтому кнопка «Стоп» в панели сервера выключена, а закрытие окна и очистка не трогают чужой процесс.

Целевая ОС: Windows 10/11 x64.

Язык интерфейса: русский (с возможностью расширения).

2. Платформа и стек
Язык: Python 3.13

GUI: PySide6 (единственный; Tkinter не используется)

Ключевые библиотеки:

requests — HTTP-запросы к llama-server

gguf — резервный путь чтения метаданных моделей; основной — собственный разбор заголовка GGUF (библиотека поднимает numpy-массив под весь файл, а нужны полтора десятка ключей из начала)

PyInstaller — сборка в .exe

Графики в «Сравнении» рисуются на QPainter, HTML-отчёты собираются строками — Jinja2 и pandas не используются, чтобы не тянуть зависимости в сборку.

Хранение: JSON-файлы (по одному на прогон набора) + HTML-отчёты + SQLite (`history.db`) для истории

3. Функциональные требования
3.1. Управление моделями
Выбор директории с моделями (.gguf) через диалог «Сменить» (кнопка рядом с путём).
Сканирование директории, вывод списка моделей с чекбоксами.
Переключатель «Модели» / «Служебные»: служебные файлы (mmproj, mtp, ggml-vocab-*) отсеиваются из основного списка — их гонять нельзя.
Выбор нескольких моделей или всех сразу (кнопки «Все» / «Снять»).
Отображение базовой информации о модели: имя, размер, параметры из GGUF (контекст, слои, квантование).
Фильтрация списка по имени (поиск над списком).

3.2. Настройка тестирования
Количество прогонов: целое число (1–10), спиннер.
Наборы тестирования (мультивыбор) — 11 штук, см. раздел 11.3:
Чат (single-turn)
Чат (multi-turn)
Агент (tools)
Скорость (tokens/sec)
Качество (golden set)
Контекст (длинный)
Function calling
Рассуждения (многошаговые)
Инструкции (жёсткие)
Устойчивость
Код
Список наборов не зашит: порядок и подписи задаёт константа, всё незнакомое, найденное на диске, дописывается по факту.
Выбор всех наборов одной кнопкой («Все») и снятие («Снять»).
Кнопка «Только упавшие» — отметить наборы, где в последнем прогоне были провалы.
Кнопка «Редактор» — открыть редактор тест-кейсов (п. 5.4).
Прогон идёт только по отмеченным наборам; «набор для редактора» (выпадающий список) на состав прогона не влияет.
Фильтр по тегам для запуска подмножества кейсов.
Лимит кейсов — N из M для быстрого прогона.
Запас на рассуждение: к бюджету ответа кейса добавляется константа (по умолчанию 2048 токенов), потому что размышление тратит тот же лимит. Без запаса модель с отдельным каналом рассуждений даёт пустой ответ, и прогон показывает провал там, где модель не виновата.
Таймаут запроса (по умолчанию 900 сек).

3.3. Режимы запуска
Через сервер: через llama-server (HTTP API) — рабочий режим.
Прямое тестирование: через llama-cpp-python (in-process) — отложено (см. п. 1). При инициализации обязательно logits_all=False для производительности.
Гибридный режим (для каждой модели свой способ) — не реализуется, пока прямой режим отложен.

3.4. Работа с llama-server
3.4.1. Выбор исполняемого файла
Поле пути + кнопка «Обзор…».

Валидация: файл существует, является .exe, при запуске --version возвращает код 0.

Автопоиск при первом запуске (директория приложения, %PATH%, %LOCALAPPDATA%\Programs\llama.cpp, C:\llama.cpp\build\bin).

Путь сохраняется в config.json.

3.4.2. Генерация команды запуска
Источник параметров (в порядке приоритета):

ручные правки пользователя (overrides);
метаданные GGUF (general.sampling.*, general.context_length);
дефолты llama.cpp.
Шаблон команды:

text
{llama-server.exe} -m "{model.gguf}" --host {host} --port {port} -c {n_ctx} --temp {temp} --top-p {top_p} --top-k {top_k} --seed {seed} -ngl {n_gpu_layers}
Отображение в редактируемом многострочном поле.

Кнопка «Сбросить к рекомендациям».

3.4.3. Управление процессом сервера
Запуск: subprocess.Popen с перенаправлением stdout/stderr в лог.

Health-check: GET /health каждые 500 мс, таймаут 60 сек.

Состояния: stopped → starting → ready → error / stopped.

Остановка: graceful terminate(), через 5 сек — kill().

Автоостановка после завершения тестов (опция, по умолчанию включена).

Защита от «зависших» процессов: при старте приложение убивает свои осиротевшие llama-server.exe (по PID из config.json).

3.4.4. Подключение к внешнему серверу
Поле host:port + кнопка «Проверить подключение».

Запрос GET /v1/models — если ответ 200, сервер доступен.

Опция «Использовать существующий сервер» — приложение не запускает свой процесс.

Конфликт портов: диалог «Порт занят. Освободить / Выбрать другой / Отмена».

3.4.5. Логирование
Отдельный раздел «Сервер» (рельс слева) с логом и цветовой маркировкой по уровням.
Кнопки: «Очистить», «Сохранить в файл», «Автопрокрутка».
Ротация лога: максимум 10 МБ, старые — в logs/.

3.5. Выполнение тестов
Последовательный запуск: набор за набором, кейс за кейсом. Один прогон — один набор.
Прогресс-бар, лог выполнения, возможность отмены.
Для серверного режима: проверка, что сервер отвечает → тесты → сохранение. Если приложение поднимало сервер само, в конце он останавливается (см. п. 4).
Сбор метрик: latency (полное время ответа), TTFT, tokens/sec, tokens_in/out, отдельно время префилла.
Скорости приходят от сервера в блоке `timings` — его отдают только сборки, понимающие `stream_options`. Если сервер их не прислал (старая сборка), стенд считает скорости сам: генерацию — как «токены ответа за время после первого токена», префилл — по времени до первого токена. Такие числа помечаются флагом `speeds_estimated` и показываются со знаком «≈»: оставлять нули значило бы показывать «0 t/s» у модели, которая выдавала сотню.
Прогрев (warm-up): 1 холостой запрос перед первым замером. Не реализовано.

3.6. Результаты и хранение
Один прогон одного набора сохраняется в отдельный JSON-файл.
Имя файла: {модель}_{набор}_{ГГГГММДД_ЧЧММСС}.json.
В каждый файл пишется batch_id — общий идентификатор запуска ({модель}_{ГГГГММДД_ЧЧММСС}). Одно нажатие «Старт» пишет столько файлов, сколько отмечено наборов, и по batch_id они собираются обратно в один прогон — и в истории, и в сравнении.
HTML-отчёт собирается автоматически после прогона набора: reports/<идентификатор прогона>.html. Для старых прогонов — по запросу (двойной клик по строке в «Истории» или по значению в «Сравнении»).
JSON содержит: модель, режим, набор и его версию, параметры, метрики, ответы, ошибки, информацию о сервере, разбивку по кейсам.

3.7. История и сравнение
Экран «История»: список прогонов (не файлов) с фильтрацией по модели/набору/дате/статусу и поиском по идентификатору.
Выбор нескольких прогонов для сравнения.
Экран «Сравнение»: столбец — прогон целиком, строка — метрика. Сводка разворачивается по наборам, набор — по кейсам.
Экспорт сравнительной таблицы в HTML/CSV.
Пагинация (10 прогонов на страницу).
Подробное описание обоих экранов — в п. 5.2 и 5.3.

4. Логика жизненного цикла сервера
Раздел описывает случай, когда приложение поднимает llama-server само (use_existing_server = false). При работе с внешним сервером (значение по умолчанию) шаги «остановить», «запустить», «дождаться health», «остановить в конце» не выполняются: приложение только проверяет, что сервер отвечает, и тестирует то, что на нём загружено. Перезапуск процесса — не его дело.

4.1. Базовые принципы
Единственный экземпляр llama-server.exe на всё время сессии тестирования.

Одна загруженная модель в памяти в любой момент.

Смена модели = смена процесса сервера (llama.cpp не умеет выгружать модель без перезапуска).

Сервер не переиспользуется между моделями.

4.2. Высокоуровневый алгоритм
text
Для каждой выбранной модели M:
    1. Остановить текущий сервер (если запущен)
    2. Дождаться полного освобождения порта и VRAM
    3. Сгенерировать команду запуска для M
    4. Запустить llama-server с моделью M
    5. Дождаться health-check (ready)
    6. Для каждого типа теста T:
         Для каждого прогона R:
             Выполнить тест
             Сохранить результат
    7. Остановить сервер
    8. Перейти к следующей модели
4.3. Детальный порядок действий
Остановка предыдущего сервера: terminate → kill (при необходимости) → ожидание освобождения порта (до 10 сек) → ожидание освобождения VRAM (до 10 сек).

Генерация команды для новой модели: параметры из GGUF + overrides.

Запуск сервера: subprocess.Popen, фиксация PID.

Ожидание готовности: опрос /health, таймаут 60 сек. При таймауте — лог stderr, пометить модель failed, перейти к следующей.

Выполнение тестов: для каждого типа и прогона; сервер не перезапускается между прогонами одной модели.

Остановка сервера: выполнить шаг 1. Если последняя модель — оставить выключенным.

4.4. Диаграмма состояний
text
[IDLE]
  │
  ▼ запуск теста
[STARTING] ──(timeout)──▶ [ERROR] ──▶ следующая модель

                        │
              да ───────┴─────── нет
              │                    │
              ▼                    ▼
        [STARTING]              [IDLE]
4.5. Переиспользование сервера
Если одна и та же модель тестируется несколькими типами тестов — сервер запускается один раз, все тесты идут подряд, потом остановка.

Перезапуск сервера происходит только при смене модели, не при смене типа теста.

4.6. Обработка исключительных ситуаций
Ситуация	Действие
Порт занят перед запуском	Диалог: «Освободить / Выбрать другой / Пропустить модель»
Сервер упал во время теста	Retry: перезапуск + повтор последнего прогона (1 раз)
Сервер не отвечает на health	Убить процесс, пометить модель failed
VRAM не освободилась	Лог + пауза 5 сек + повторная проверка (до 3 раз)
Пользователь нажал «Отмена»	Завершить текущий тест, остановить сервер, сохранить частичные результаты
Краш приложения	При следующем старте — убить осиротевший llama-server.exe по PID из config.json
4.7. Псевдокод основного цикла
python
def run_testing_session(models, test_types, runs):
    server = ServerManager(config)
    for model in models:
        try:
            server.stop()
            server.wait_resources_free()
            cmd = build_command(model)
            server.start(cmd)
            if not server.wait_ready(60):
                log_error(model, "startup_timeout")
                continue
            for test_type in test_types:
                for run in range(runs):
                    result = run_test(model, test_type, run)
                    save_json(result)
        except CancelledByUser:
            break
        finally:
            server.stop()
    server.cleanup()

### 4.8.1. Блок `memory` — расход памяти модели

Отдельный от `server` блок: `server` описывает процесс, `memory` — куда легла модель. Пишется в файл прогона, если удалось прочитать лог загрузки.

json
"memory": {
  "source": "load-log",
  "model_path": "F:/Models/Qwen3.5-0.8B.Q8_0.gguf",
  "vram_mib": 907.42,
  "ram_mib": 9.81,
  "disk_mib": 257.66,
  "buffers": {"CPU_Mapped model": 257.66, "CUDA0 model": 763.78, "CUDA_Host output": 3.79, "CUDA0 KV": 24.0, "CUDA0 RS": 77.06, "CUDA0 compute": 42.58, "CUDA_Host compute": 6.02},
  "layers": {"CUDA0": 25},
  "layer_devices": {"0": "CUDA0", "1": "CUDA0", "24": "CUDA0"},
  "layers_total": 25,
  "offloaded": 25,
  "output_on_gpu": false,
  "devices": {"CUDA0": {"name": "NVIDIA GeForce RTX 5060 Ti", "total_mib": 16283.0, "free_mib": 15172.0}}
}

Откуда берутся цифры. По HTTP их не отдаёт ни `/props`, ни `/metrics`: llama-server печатает раскладку буферов и слоёв **только в stdout при загрузке модели**. Разбор — `llmtestbench/server_log.py`, читает `logs/server.log` (его ведёт `server_manager._reader_loop`).

Правила разбора:

- Буферы печатаются **дважды**: сначала обнулённый проход подгонки, потом настоящий. Побеждает последнее значение.
- Буферов семь, и три плитки — это их суммы: VRAM = `CUDA0 model` + `CUDA0 KV` + `CUDA0 RS` + `CUDA0 compute` = 907.42; RAM = `CUDA_Host output` + `CUDA_Host compute` = 9.81; диск = `CPU_Mapped model` = 257.66.
- Устройство определяет корзину: `CPU_Mapped` → диск (веса остаются в файле, mmap), `CPU*` и `*_Host` → RAM, остальное → VRAM. `CUDA_Host` — это host-буфер, то есть RAM, несмотря на имя.
- Разбор **построчной раскладки слоёв** (`layer N assigned to device X`) требует запуска сервера с `-v`. На `-lv 4` есть только буферы, без `-v` — вообще ничего.
- Если про память в логе нет ничего, `parse_load_log` возвращает `None`, а в JSON остаётся пустой `{}`. Пустой словарь — «не измерено», а не ноль: в отчёте это строка «нет данных». Ноль VRAM у работающей модели читался бы как ошибка замера.
- Лог сервера дописывается между запусками, поэтому в нём может лежать загрузка **другой** модели. Перед записью имя файла из лога сверяется с моделью прогона (`TestRunner._memory_matches`); не сошлось — блок не пишется.
- Лог есть только у сервера, поднятого самим приложением. При работе с внешним сервером (`use_existing_server: true`) блока не будет — это нормальное состояние, а не сбой.

5. UI-экраны
Разделы переключаются рельсом слева (не вкладками сверху). Разделов четыре: Тестирование, Сервер, История, Сравнение. Рельс сворачивается до иконок (Ctrl+B), состояние запоминается.

5.1. Главное окно (раздел «Тестирование»)
Слева: панель моделей (путь + «Сменить», поиск, переключатель «Модели»/«Служебные», список с чекбоксами, кнопки «Все», «Снять»).
В центре: настройки тестирования (прогоны, наборы, теги, лимит кейсов, запас на рассуждение, таймаут).
Справа: настройки сервера (путь к llama-server.exe, host:port, команда запуска, кнопки «Запустить», «Стоп», «Сбросить команду», статус сервера).
Внизу: полоса прогона (прогресс, остаток времени, кнопки «▶ Старт» / «■ Стоп») и сворачиваемый журнал выполнения.
Строка состояния: сервер, модель, наборов/кейсов.

5.2. Раздел «История»
Фильтры (применяются сразу, кнопки «Применить» нет): модель, набор, период (по умолчанию последний месяц), статус, поиск по идентификатору.
Кнопки «Сбросить» и «Обновить».
Таблица: строка — прогон целиком, а не файл. Колонки: флажок, прогон, модель, набор, счёт, время, дата, статус, действие.
Клик по заголовку сортирует по столбцу, повторный — меняет направление.
Разворот прогона по треугольнику: строки кейсов — идентификатор, название, вердикт, время, причина провала. Показываются первые 15 кейсов, остаток — строка «ещё N кейсов» (двойной клик по ней открывает отчёт прогона).
Двойной клик по строке прогона — HTML-отчёт по всем его наборам; по строке кейса — карточка кейса (задание, ответ, рассуждение, разбор проверки, метрики).
Панель действий появляется при выделении: «Выделить все» / «Снять выделение», «Сравнить выбранные», «В корзину».
«Сравнить выбранные» активна при двух прогонах и более: один прогон из семи файлов — это один столбец, сравнивать его не с чем.
Удаление — в корзину, а не безвозвратно; записи из базы удаляются вместе с файлами.
Цветовая маркировка статуса: зелёный «Готово», жёлтый «Остановлен», красный «Сбой», серый «Без проверок».
Пагинация: 10 прогонов на странице.

5.3. Раздел «Сравнение»
Панель инструментов: «Только различия», «Графики», «Открыть JSON…», «Экспорт в HTML», «Экспорт в CSV», печать.
Столбец таблицы — прогон целиком (не тест и не файл). Файлы собираются в прогоны той же группировкой, что в «Истории», поэтому столбцов ровно столько, сколько прогонов отмечено там. Порядок хронологический: слева ранний, справа поздний.
Строки метрик: Прогон (дата), Модель, Размер модели, Контекст, Наборов, Кейсов, Качество, Сбои стенда, Пустых ответов, Префилл (avg), Tokens/sec (avg), Latency (avg), TTFT (avg), Время прогона, Версии наборов, Итоговый рейтинг.
Скорость префилла — отдельная строка, а не «ещё одна скорость»: на длинных контекстах модели различаются именно ею, тогда как генерация у них держится примерно одинаково.
Знак «≈» у скорости означает, что число посчитано стендом по своим замерам, а не пришло от сервера (см. п. 3.5).
Лучшее значение в строке помечается «★» только тогда, когда значения различаются: одинаковые звёзды у всех — шум, а не победа.
«Только различия» прячет строки, где у всех прогонов совпал показанный текст.
Детализация — разворот строки: клик по подписи (где треугольник) показывает подстроки по наборам. Наборы идут в порядке первого появления по всем прогонам; набор, которого в прогоне не было, стоит прочерком.
Двойной клик по значению подстроки набора — покейсовое сравнение набора по всем прогонам: строки — кейсы, столбцы — прогоны, вердикты ✔ зачтён / ✘ провал / ⚠ сбой стенда / – пропуск / — кейса не было. Двойной клик по ячейке — карточка кейса.
Прогоны, которые набор не гоняли, в покейсовую таблицу не попадают — они перечислены в подписи.
Предупреждение (п. 11.7): если у сравниваемых прогонов набор записан в разных версиях, сверху появляется полоса с перечислением таких наборов. В HTML-выгрузку предупреждение попадает вместе с таблицей.
Два графика: tokens/sec и latency по кейсам прогонов. Ось X — порядковый номер кейса, а не название набора: у разных прогонов наборы идут разным порядком.

6. Обработка ошибок
Ситуация	Поведение
Модель не найдена	Пропустить, записать в JSON error: "model_not_found"
GGUF повреждён	Пропустить, лог + запись в отчёт
llama-server не стартует	3 попытки, затем пометить модель как failed
Таймаут health-check	Остановить процесс, записать error: "startup_timeout"
Ошибка HTTP при тесте	Retry 2 раза, затем записать в результат
Нехватка VRAM	Предупреждение + предложение снизить -ngl
Прерывание пользователем	Сохранить частичные результаты, статус cancelled
Диск заполнен	Блокировка запуска, диалог с предложением очистить results/

Состояние на сегодня: таймаут health-check, сбой стенда, прерывание пользователем и осиротевшие процессы обрабатываются как описано. Повтор при HTTP-ошибке во время теста есть, но узкий: `local_agent.complete()` делает до 3 попыток с паузой 5 с и только на «инфраструктурных» ошибках (503, `loading model`, `connection refused/reset/aborted`, `no route to host`, `unavailable_error`) — содержательная ошибка сразу пишется в результат. Освобождение VRAM проверяется до 3 раз (`RESOURCE_RETRIES` в `server_manager.py`). При старте сервера повторов нет: `wait_for_port` ждёт до таймаута и сдаётся. Проверки свободного места на диске тоже нет.

Добавлено сверх описанного (раздел 10, пункт 11): все файлы — результат прогона, HTML-отчёт, конфиг, экспорт из редактора, журнал сессии субагента — пишутся через временный файл рядом с целевым и `os.replace`. Это делает запись атомарной: обрыв прогона, закрытие окна или нехватка места не оставляют обрезанный JSON. Ошибки, которые раньше исчезали без следа, теперь попадают в лог приложения (`logs/app.log` с ротацией по 2 МБ), а не в два `print()` в библиотеке.

9. Краевые случаи
Очень длинные имена моделей — обрезка в UI с tooltip.
Модели > 50 ГБ — предупреждение о времени загрузки. Не реализовано.
Кириллица в путях — полная поддержка UTF-8. Реализовано, включая чтение вывода сервера байтами с декодированием UTF-8 (построчное чтение с decode_unicode портит русский текст).
Запуск без GPU — автоопределение и fallback на CPU с предупреждением. Не проверялось на целевой машине: GPU есть, поведение без него не воспроизводилось.
Одновременный запуск двух экземпляров — блокировка через mutex. Не реализовано.

11.2. Формат тест-кейса
Каждый тест-кейс — отдельный JSON-файл:

json
{
  "id": "chat_single_001",
  "name": "Приветствие",
  "prompt": "Привет! Как тебя зовут?",
  "expected": {
    "type": "contains_any",
    "values": ["ассистент", "помощник", "AI", "языковая модель"]
  },
  "params": {
    "temperature": 0.0,
    "seed": 42,
    "max_tokens": 128
  },
  "tags": ["basic", "identity"],
  "weight": 1.0
}
Поля:

id — уникальный идентификатор.

name — человекочитаемое имя для логов и отчётов.

prompt — входной текст (или список сообщений для multi-turn).

expected — критерий проверки (см. 11.4).

params — переопределение параметров сэмплирования для конкретного кейса.

tags — для фильтрации.

weight — вес при подсчёте итогового скора.

11.3. Наборы тестов
11.3.1. Чат single-turn
Набор: 20 кейсов разной сложности (факты, рассуждения, инструкции, креатив).

Метрики: latency, tokens/sec, tokens_in/out, длина ответа.

Проверка: contains_any, contains_all, regex, not_contains, exact_match, llm_judge.

Пример кейса: «Назови три столицы Европы» → expected: contains_all: ["Париж", "Лондон", "Берлин"].

11.3.2. Чат multi-turn
Набор: 6 сценариев по 3–5 реплик.

Формат prompt: массив [{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}, ...].

Проверка: модель должна удерживать контекст предыдущих сообщений.

Пример: пользователь называет имя в первом сообщении, спрашивает о нём в третьем → expected: contains: "имя".

11.3.3. Агент (tools)
Набор: 10 сценариев с описанием доступных инструментов.

Схема инструментов: tools_schema.json в формате OpenAI function calling.

Проверка: правильность выбора инструмента, корректность аргументов, следование цепочке. Есть проверка no_tool_call — «инструмент не нужен, ответ должен быть текстом».

Пример: «Какая погода в Москве?» → expected: tool_call: {"name": "get_weather", "arguments": {"city": "Москва"}}.

11.3.4. Скорость (speed)
Набор: 6 промптов фиксированной длины — 100, 500, 1000, 4000, 16000, 32000 токенов. Промпт не хранится, а собирается генератором: содержание не важно, важна ровная длина, иначе замеры несравнимы между собой. Длинные префиллы (16K, 32K) показывают, где начинают сказываться память и шина, а не только вычислительная мощность.

Метрики: tokens/sec, latency до первого токена (TTFT), общее время генерации.

Особенность: каждый промпт прогоняется N раз, считается среднее и стандартное отклонение.

Warm-up: 1 холостой прогон перед замерами.

11.3.5. Качество (golden set)
Набор: 8 эталонных вопросов с экспертными ответами (tests/quality/golden/).

Проверка: автоматическая оценка через:

BLEU / ROUGE — не реализовано.

LLM-as-judge — для открытых (промпт с эталоном даётся судье).

Embedding similarity — зарезервировано, не реализовано.

Формат expected:

json
"expected": {
  "type": "llm_judge",
  "golden": "Эталонный ответ...",
  "judge_prompt": "Оцени ответ от 0 до 10 по критериям...",
  "min_score": 7
}
11.3.6. Контекст (длинный)
Набор: 10 кейсов с ростом контекста — 2K, 4K, 8K, 16K, 32K, 64K, 128K токенов, плюс три особых: дистрактор (два похожих кода доступа, взять нужно нужный, а не первый попавшийся), коды на самых краях текста, вопрос про код, которого в документе нет.

Метрики: latency, tokens/sec, качество ответа на «иголку в стоге сена» (needle in haystack).

Проверка: модель должна найти ключевую информацию в длинном тексте.

Текст-наполнитель — tests/context_long/haystack/, около 26K токенов, поэтому для 64K и 128K пул повторяется. Иголка остаётся единственной, но избыточность текста делает эти два кейса мягче, чем 32K.

11.3.7. Function calling
Набор: 10 вызовов функций с параметрами разной сложности (tests/function_calling/functions/).

Схема: JSON Schema для каждой функции.

Проверка: валидность вызова по схеме, корректность типов, отсутствие галлюцинаций параметров.

11.3.8. Рассуждения (reasoning)
Набор: 8 многошаговых задач, где ответ нельзя получить одним действием: две наценки подряд, расселение по условиям, день недели через 100 дней, порядок старшинства, секунды в часах, рукопожатия, задача без единственного ответа.

Проверка: all_of — числовой ответ, отсутствие лишних данных, признание неоднозначности там, где она есть.

Зачем: наборы на знание такие модели проходят почти без ошибок; расходится дисциплина рассуждения, а не эрудиция.

11.3.9. Инструкции (instruction_following)
Набор: 8 кейсов на точное выполнение формы: пять слов на одну букву, ровно три пункта, три страны вне ЕС, строгий JSON-план, один вариант перевода, порядок этапов, ответ словом без цифр, строка строго по шаблону.

Проверка: word_count, set_equal, regex, json_schema, all_of.

11.3.10. Устойчивость (robustness)
Набор: 6 кейсов на поведение в неудобных условиях: инъекция внутри письма, уверенное неверное утверждение (проверка на поддакивание), несуществующий метод библиотеки, неполное задание, противоречивое задание, просьба о недопустимом действии.

Проверка: модель не выполняет встроенную инструкцию, не подтверждает ложь, называет пробел в задании, а не выдумывает ответ.

11.3.11. Код (code)
Набор: 5 кейсов: поиск причины ZeroDivisionError, результат среза x[::-1][1], сложность вложенных циклов, функция dedup с выводом, ошибка в регексе даты.

Проверка: all_of — верный ответ и наличие требуемой конструкции.

11.4. Типы проверок (expected.type)
Тип	Описание	Пример
contains_any	Ответ содержит любое из значений	["Париж", "Paris"]
contains_all	Ответ содержит все значения	["решение", "пример"]
not_contains	Ответ не содержит значений	["не знаю", "извините"]
regex	Соответствует регулярному выражению	"\\d{4}-\\d{2}-\\d{2}"
exact_match	Полное совпадение (нормализованное)	"42"
json_schema	Ответ — валидный JSON по схеме	схема в schema
tool_call	Правильный вызов инструмента	{"name": "...", "arguments": {...}}
no_tool_call	Ответ НЕ является вызовом инструмента (инструмент не нужен)	{"name": "get_weather"}
all_of	Выполнены все вложенные проверки сразу	{"checks": [{"type": "regex", ...}, {"type": "not_contains", ...}]}
word_count	Нужное число слов (exact / min / max)	{"min": 5, "max": 5}
set_equal	Ответ перечисляет ровно заданный набор, порядок не важен	{"values": ["Париж", "Лондон", "Берлин"]}
llm_judge	Оценка через отдельную LLM	{"golden": "...", "min_score": 7}
embedding	Косинусная близость ≥ порога — зарезервировано, не реализовано	{"golden": "...", "min_similarity": 0.85}

Два общих правила, действующих для всех типов:

Пустой ответ — провал при любой проверке, до разбора типа. Иначе «модель промолчала» проходило бы проверку not_contains.
Markdown-обёртка вокруг JSON (```json ... ```) — нарушение формата, даже если внутри валидный JSON.
Сбой стенда (запрос не доехал, сервер упал) — не провал модели: он не идёт в знаменатель и отмечается отдельно.
Пропуск не равен провалу: llm_judge и embedding без судьи дают passed=None и в знаменатель не попадают.
all_of — основной инструмент для сложных кейсов: одна задача почти всегда требует нескольких условий разом («ответь JSON'ом, ровно пять элементов, без латиницы»).

11.6. Импорт и экспорт тестов
Импорт из JSON: одна кнопка подгружает кейсы из внешнего файла в текущий набор.
Импорт из CSV: для простых наборов (prompt, expected, tags).
Импорт из YAML — не реализовано.
Экспорт: текущий набор → JSON / CSV.
Валидация при импорте: проверка схемы, дубликатов id, наличия обязательных полей. На диск пишутся только вновь добавленные кейсы — существующие файлы не перезаписываются, иначе при смене нумерации имён в cases/ появлялись бы дубликаты.

11.7. Версионирование тестов
Каждый набор имеет поле version в manifest.json.
При изменении набора — инкремент версии (1.0.0 → 1.0.1 для правок, 1.1.0 для новых кейсов). Текущая версия всех наборов — 2.0.0.
В результатах JSON фиксируется версия набора (set_version), чтобы сравнение было корректным.
При сравнении прогонов, у которых версии набора разошлись, — предупреждение в UI (полоса над таблицей с перечислением наборов) и в HTML-выгрузке.

11.8. LLM-as-judge
Судья — тот же llama-server с другим промптом; задаётся один раз на набор, в блоке scoring из manifest.json, а не отдельным полем у каждого кейса.

Источник: локальная модель (через llama-server).
Промпт судьи: задаётся в manifest.json набора.
Параметры: temperature=0, фиксированный seed.
Судья возвращает число 0–10, оно сравнивается с min_score — это и есть вердикт кейса.
Запасной путь: если судья недоступен или вернул не число, runner откатывается на keyword-проверку из expected (fallback). Это не провал модели: score=None и текст ошибки.
Кэш оценок — не реализовано.
Калибровка судьи по эталонной разметке — не реализовано.

11.9. Формат manifest.json набора
json
{
  "id": "quality",
  "name": "Качество ответов (golden set)",
  "version": "2.0.0",
  "description": "Сравнение с эталонными ответами через LLM-as-judge",
  "cases_count": 8,
  "metrics": ["latency_ms", "tokens_per_sec", "judge_score"],
  "scoring": {
    "type": "llm_judge",
    "judge_model": "local",
    "judge_prompt": "Оцени ответ от 0 до 10 по критериям: точность, полнота, отсутствие галлюцинаций. Верни только число.",
    "min_score": 7,
    "aggregate": "mean",
    "fallback": "contains_all"
  },
  "default_params": {
    "temperature": 0.0,
    "seed": 42,
    "max_tokens": 384
  },
  "tags": ["quality", "golden", "hard"]
}

Поля:

scoring — либо строка "none" (набор без оценки судьёй), либо объект: type, judge_model, judge_prompt, min_score, aggregate, fallback.
generator — у наборов, где промпт не хранится, а собирается (speed, context_long). Кейсы таких наборов не содержат prompt, а содержат generator и target_tokens.
tags — для фильтрации кейсов при прогоне.
